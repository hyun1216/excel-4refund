```text
[1차: 원천자료 수집·정규화]
작업명령/회사/연도 확인
  → 세무프로그램에서 회사정보·원천징수영수증·급여대장 추출

  → 지급·공제 항목 목록 생성
  → 기초정보(1차) 작성

[사람 검토 1]
지급항목을 정액급여/수당검토로 분류
사번·주민번호 중복 및 인적사항 확인

[2차: 수당분류 반영·급상여현황 생성]
검토된 기초정보(1차) 수신
  → 비과세 항목 및 수당 분류 반영
  → 연도별 급상여현황 생성
  → 기초정보(2차)·샘플 이미지 작성

[사람 검토 2]
대상자/비대상자 확정
비과세 항목 추가 및 금액 조정
급상여현황(수정)·기초정보(3차) 준비

[3차: 수정신고 결과물 생성]
급상여현황(수정)으로 월별 급여·상여대장 생성
  → 기초정보(3차)의 사업장·수당·조정정보 읽기
  → 수정 전 원천징수영수증 이미지화
  → 수정 원천징수영수증 생성
  → 수정 결과를 다시 추출해 기초정보(최종) 갱신
  → 국세청·공단 추가서류 생성
  → 환급대상자 전용 제출 임금대장 생성
  → 수정 전/후 원천징수영수증 분류
  → 배포 ZIP 및 검증목록 생성
```

| **30. 수정 전/후 영수증 분류** | `filterSubmitPAYE`가 제출용 폴더로 양쪽 PDF 이동/복사 | **부분 구현**<br>S40 산출물과 원본은 있으나 기관별 제출 구조 자동분류는 미완성 | 국세청/공단별 폴더 계약 및 누락·중복 대조표 필요 |
| **31. 최종 ZIP·무결성** | 결과물 전달 | **구현**<br>S70이 허용된 단계만 모아 ZIP과 SHA-256 manifest 생성 | S50/S60 미완성 때문에 현재 정상 완료 불가. 부분 성공을 성공으로 표시하지 않음 |

## 4. 현행 구현이 실제로 확인된 범위

### 급여대장 정규화 별도 도구

- 대상 PDF 26개
- 통과 24개, `NEEDS_REVIEW` 2개, 실패 0개
- 직원 행 6,456개
- 일반적인 `인적사항 / 기본급여 및 제수당 / 공제 및 차인지급액` 3행 머리글을 인식한다.
- 2025년 7월·10월 자료는 원본 합계가 비어 있어 자동 성공시키지 않고 검토 대상으로 남긴다.
- 이 결과는 **별도 프로젝트의 검증 결과**이며 현재 `payroll_amendment` 실행에 자동 연결되지는 않는다.

### 현행 3차 Python 흐름

- S10: 입력 스냅샷·SHA-256 manifest, 회사·연도·대상자·비과세 정보 로드
- S20: 월별 급여/상여대장 16개, 총 4,098행 생성 확인
- S30: 대상자 102명, 원천징수 이미지 312개 생성 확인
- S40: 수정 원천징수영수증 102개 및 처리결과 대조표 생성 확인
- S50: 승인 템플릿과 `document_specs.json` 부재로 `E_RULE_NOT_IMPLEMENTED`
- S60: 월별 대장 복사 수준이며 `NEEDS_REVIEW`
- S70: S50/S60이 완료 상태가 아니어서 최종 성공 ZIP을 막음

즉, 현재 확인된 종단 흐름은 `완성된 기초정보(3차)+급상여현황(수정)+개인별 원천징수 PDF`를 받아 월별 대장·이미지·수정 영수증까지 만드는 구간이다. 원자료에서 기초정보와 급상여현황을 만드는 1·2차는 본 흐름에 없다.

## 5. 디테일 기준 누락·구현 점검

### 입력·파일 구조

구현된 부분:

- 다년도 원천징수 PDF를 연도별로 탐색한다.
- 파일명 끝 숫자 인덱스 중복을 차단한다.
- 입력 원본을 실행 폴더에 복제하고 해시를 남긴다.
- 수정본이 다시 원본 후보로 섞이는 것을 방지한다.

누락 또는 보완할 부분:

- 묶음 PDF를 개인별로 분할하는 규칙
- 번호 없는 PDF 번호 부여와 원상복구
- 같은 연도에 기초정보/급상여현황 후보가 여러 개일 때의 확정 규칙
- 연도 누락, 월 누락, 같은 월 중복, `_1`, `_2` 등 분할 급여대장의 통합 검증
- 수정 전 원천징수영수증이 대상자 전원에게 존재하는지의 시작 전 일괄 검사

### 급여대장 정규화

구현된 부분(별도 도구):

- 일반 3행 머리글과 기존 레이아웃을 함께 지원
- 지급/공제를 원본 그룹 머리글 경계로 분리
- 합계·페이지·원본파일 추적 열 유지
- 빈 합계 자료를 `NEEDS_REVIEW`로 차단

누락 또는 보완할 부분:

- 현행 본 파이프라인으로 통합
- 정규화 결과의 머리글·매핑 미리보기와 사용자 승인 저장
- 주민번호 없는 급여대장의 직원 매칭 정책
- 입·퇴사월, 중도입사, 상여, 소급·환수, 음수·0원 처리 규칙
- 검토 상태의 파일이 수당분류·세액 작업으로 넘어가지 못하게 하는 승인 게이트

### 수당 분류·급상여현황

구현된 부분:

- 이미 확정된 비과세 항목·금액을 읽어 후속 영수증 수정에 사용
- 이미 수정된 급상여현황에서 월별 대장을 생성

누락 또는 보완할 부분:

- 지급항목 목록 자동 생성

## 7. 구현 전에 사용자 확인이 필요한 세부 규칙

아래는 코드가 추측하면 안 되는 항목이다.

1. 세무사랑 자동 다운로드까지 포함할지, 사용자가 내려받은 파일부터 시작할지
2. 급여대장에 주민번호가 없을 때 `사번+성명`을 확정키로 쓸 수 있는지
3. 같은 달의 급여/상여/추가지급/소급/환수 구분 규칙
4. 지급항목별 정액급여·상여·과세·비과세 분류표와 비과세 한도
5. 입사월·퇴사월·휴직·중도정산·음수·0원 처리 규칙
6. 원본 합계가 비어 `NEEDS_REVIEW`인 월의 대조 근거와 승인자
7. 대상자 선정 기준 및 비대상자 보존 방식
8. 추가서류의 실제 최종 템플릿과 필수 기재 항목
9. 국세청/공단 제출 임금대장의 정확한 열 순서·시트 구성·파일명
10. 수정 영수증의 비과세 외 수정 대상 필드와 반올림 규칙

이 열 가지가 확정되지 않으면 1·2차 자동화와 S50/S60을 ‘완료’로 판정할 수 없다.

## 8. 최종 결론

현행 구현은 Brity/VBA 전체 흐름을 대체한 상태가 아니다. **3차 후반의 월별 대장 생성, 수정 전 영수증 이미지화, 대상자 검증, 수정 영수증 별도 생성은 구현·실자료 검증되었다.** 반면 **1차 원자료 수집·원천징수 추출·기초정보(1차), 2차 수당분류·급상여현황 생성, 3차 추가서류와 대상자 전용 제출 임금대장**은 누락 또는 부분 구현이다.

Google Drive와 이메일은 사용자 요청에 따른 의도적 제외이므로 누락으로 보지 않는다. 더존 자동추출 분기는 원본 Brity에서도 핵심 작업이 비활성 상태라 현재의 기준 구현 범위로 잡지 않는 것이 타당하다.
